## 二、先处理两个现有代码问题

### 问题 1：不要将 A* 重放一致性断言直接降级为警告

这是我最想提醒 AI Agent 的地方。

现在的 `ragc_oracle_pilot.py` 已经将 `replay_fp_maxdiff` 作为诊断信息记录，但仍对 Anchor RGB、原动作分支的完整后续动作序列和成功性执行严格检查。

![](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com\&sz=32)

GitHub

我建议保留这些严格检查。

ep7 的问题不应该通过“忽略异常，然后继续生成训练标签”解决。

因为我们训练的是：

Qϕ(zt,g,A)≈Creal(A)Q_\phi(z_t,g,A) \approx C_{\mathrm{real}}(A)Qϕ(zt,g,A)≈Creal(A)

如果 A* 的真实执行结果都无法可靠复现，那么同一 Anchor 上的正负扰动代价也可能不可信。

正确的做法是：

将异常 Anchor 标记为 Invalid、保存错误信息、跳过其训练标签，但允许后续任务继续运行。

例如，在 `ragc_oracle_pilot.py` 中，将每个 Anchor 的严格验证改为类似：

Python

运行

```
try:
    np.testing.assert_allclose(
        results[0]["raw_executed"],
        remaining_original,
        rtol=0,
        atol=1e-6,
    )

    if results[0]["success"] != trace["success"]:
        raise AssertionError(
            "Baseline replay success mismatch"
        )

except AssertionError as exc:
    record = {
        "episode": ep_i,
        "step": entry["step"],
        "valid": False,
        "reason": str(exc),
    }

    append_jsonl(output_path, record)

    # 该 Anchor 不进入训练集
    continue
```

这段代码是修改示意，需要 Agent 放进现有循环并处理上下文变量。

关键是：继续执行后续 Episode，不等于允许无效标签进入数据集。

我建议针对 ep7 做一次单独调试，记录首次轨迹分歧的位置、动作是否变化，以及分叉前的物理状态指纹。

还有一个需要注意的事实：你的修复使反事实分支之间的 Anchor Spread 降为零，但这只证明分支之间一致，不自动证明它们与官方实际执行时的完整隐藏状态一致。

因此，不应仅凭 `anchor spread=0` 就放弃原始动作重放检查。

### 问题 2：必须解决中途失败导致数据丢失

我查看了当前 `ragc_oracle_pilot.py`，它确实是在循环全部结束后才统一写出 JSON 和 NPZ。只要前面某个任务抛异常，本次运行已经完成的数据就可能不会保存。

![](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com\&sz=32)

GitHub

考虑到你的完整反事实继续执行比较昂贵，我认为这项修改必须优先完成。

建议增加一个简单的逐 Anchor JSONL 保存函数：

Python

运行

```
import json
import os
from pathlib import Path


def append_jsonl(path, record):
    path = Path(path)
    path.parent.mkdir(parents=True, exist_ok=True)

    with path.open("a", encoding="utf-8") as f:
        f.write(
            json.dumps(record, ensure_ascii=False)
            + "\n"
        )
        f.flush()
        os.fsync(f.fileno())
```

每个 Anchor 完成后，立即保存：

* `valid`：是否通过重放门禁。

* `task_id`、`anchor_id`、`steps_taken`。

* Baseline 成功与候选成功向量。

* 每个候选的 Realized Cost。

* A* 重放误差与物理指纹差异。

* 当前实验 Commit、Checkpoint、随机种子。

大规模张量和 Latent 可以按任务单独保存为 NPZ，最后再合并。

这样，即使第 10 个任务失败，前 9 个任务的数据依然完整。

### 不要只收集失败任务

这点尤其重要。

RAGC 不只需要学会：

> 什么动作能够救回失败任务？

还需要学会：

> 哪些修改会破坏原本能够成功的任务？

上一轮 12 个开发任务中有 4 个原始成功任务，但成功任务的扰动脆弱性尚未完成统计。

因此 Stage 1 的训练数据应该包含原成功与原失败状态，而不能只针对失败任务生成标签。

否则，网络可能倾向于频繁修改动作，导致救回一部分失败任务的同时破坏更多原成功任务。

我们最终关心的是净成功数，而不是单方面的救回数。

有个容易忽略的细节：

如果两种候选都失败，仍然可能具有不同的连续任务代价。

这些样本可以帮助网络学习动作方向，但不能把它们等同于真实成功率改善。

相反，如果大量样本的 ΔC\Delta CΔC 都非常接近零，那么即使已经采集了很多轨迹，RAGC 也可能得不到有效的局部梯度监督。

这时应该停止扩大数据，先审查监督信号，而不是立即增加 Head 的深度。
